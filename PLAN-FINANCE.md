> ПОРЯДКУ — каждый опирается на предыдущие. Один шаг = один коммит.
> Шаг закрыт только когда: `php artisan test` зелёный, `npm run build`
> чистый, новые строки UI переведены на казахский (см. §D).

# Часть I. Обязательные правила (действуют в каждом шаге)

## §A. Адаптация под Qazaq Tas

- Одна фирма **QT**. Механизм `companies`/`CurrentCompany` сохранён — новый
  код пишем с теми же скоупами (`CurrentCompany::id()`, `worksInCompany`),
  режимов «двух фирм» не изобретаем. Касса — ЕДИНАЯ, банк — скоуп фирмы
  (правило проекта, совпадает с BAIA).
- Терминология: «Заявки / запросы КП» (не «лоты»), designer=«Технолог»,
  supplier=«Снабженец». Три города-филиала к финансам отношения не имеют.
- Деньги — один источник правды: `PayrollService` + `FinanceService`. Все
  новые цифры — через них. Запрос «мимо сервисов» = расхождение страниц.
- Уведомления пишутся по-русски (язык фиксируется при создании — известное
  ограничение проекта, новые следуют ему же).

## §B. Безопасность (проверяется в каждом шаге)

1. **Политики с ролями, не только permissions.** Критичные запреты
   дублируются `hasAnyRole()` внутри Policy — чтобы держались, даже если
   права поменяют через админку.
2. **Чеки — приватные.** Файлы лежат в `storage/app/private`
   (`->store('receipts', 'local')`), отдаются только через guard-маршрут с
   проверкой: автор / сотрудник из выплаты (`employee_id`) /
   admin, director, financist. Прямых ссылок в `public/` нет.
3. **Загрузка файлов** — правила как у существующих чеков (mimes
   jpg,jpeg,png,webp,pdf; max по образцу текущего `ExpenseRequest` /
   confirm-валидации — посмотреть и переиспользовать, не изобретать).
4. **IDOR-тесты обязательны**: чужой id в адресе не открывает чужие данные
   («Мои расходы», чек чужой заявки, долг чужого сотрудника).
5. **Гонки** — `DB::transaction` + `lockForUpdate` на всех операциях
   «прочитал остаток → записал» (платёж по счёту, «В работу ✓», списание
   долга). Идемпотентность команд — на unique-ключах БД, не на if-ах.
6. **Mass assignment** — только `$fillable`; `status`, `payment_method`,
   `confirmed_by`, `employee_id` НЕ принимаются из формы там, где их ставит
   сервер (заявка сотрудника, авто-расходы).
7. **Аудит**: новые денежные операции (выдача долга, списание долга,
   оплата закупа, подтверждение заявки) попадают в существующий аудит-лог
   тем же механизмом, что нынешние расходы. Удаление финзаписей продолжает
   слать уведомление СЕО/директору (`FinanceAudit::notifyDeleted`).
8. Сотрудник (цех/юрист/повар) сумм сделок НЕ видит — «Мои расходы»
   показывают только его собственные заявки и выплаты, ничего про сделки.

## §C. Скорость (проверяется в каждом шаге)

1. **Индексы сразу в миграции**: `expenses.employee_id`,
   `expenses(employee_payout)`, `employee_debt_payments` unique(долг,
   месяц), `employee_debts.user_id`. Составные `status+payment_method` на
   expenses уже есть — не дублировать.
2. **Eager loading**: каждая новая выборка — с `with()`; проверка на N+1
   глазами по запросам страницы (`->with('category:id,name',
   'responsible:id,name', 'employee:id,name')` и т.п.).
3. **Кассовая книга** ограничивает выборку ОДНИМ днём (where date = ?),
   остаток на начало — три агрегатных SUM-запроса до даты, не загрузка
   всех записей в память.
4. **Аккордеоны** для «прошлых» записей (как на Финансах): сегодняшнее
   сверху, прошлое — свёрнуто с ленивой подгрузкой только если это уже так
   сделано у соседей; новых поллингов НЕ добавлять.
5. Деньги считает СЕРВЕР; клиент только показывает. Никаких пересчётов
   больших массивов в computed на каждый рендер.
6. Код-сплит по страницам даёт Inertia автоматически — не тащить тяжёлые
   импорты в общие компоненты.

## §D. Двуязычие KZ/RU (ворота каждого шага)

- Каждая видимая строка ERP — `$e('Русский текст')` в шаблоне / `tr('…')`
  в script (`const tr = useE()` из `@/composables/useTranslations`).
- Каждая новая строка добавляется в `lang/kk/erp.php` с казахским
  переводом (ключ = русский текст, файл отсортирован по ключу).
- Сторожевые тесты `ErpInterfaceLocaleTest` сверяют шаблоны и словарь В ОБЕ
  СТОРОНЫ и упадут сами при пропуске. НЕ отключать, НЕ ослаблять — чинить
  словарь.
- `defineProps` значения по умолчанию — БЕЗ `tr()` (defineProps поднимается
  выше setup); русский литерал там служит ключом, перевод — в месте показа.

- **Модалки**: ТОЛЬКО существующий `Components/Modal.vue` (анимация уже

## §F. Анимации (правила проекта — не нарушать)

- Только `transform` и `opacity` — раскладку не анимируем (правило
  PROJECT.md §6, действует и в ERP).
- Микро-переходы: `transition-colors duration-150` на hover,
  `transition-shadow` на карточках борда (`hover:shadow-md`),
  `transition-opacity` на действиях.
- Появление/скрытие блоков (аккордеоны, фильтры) — `<Transition>` c
  `enter-from-class="opacity-0 -translate-y-1"` и `duration-200..300`,
  по образцу мобильного меню/модалки.
- Смена статуса заявки на борде — карточка уходит через
  `<TransitionGroup>` (opacity + translate), список не «прыгает».
- Плитки-цифры НЕ анимировать счётчиками; большие таблицы НЕ анимировать
  вовсе. Вечных/зацикленных анимаций не добавлять.
- `prefers-reduced-motion` уважается там, где анимация длиннее 300мс.

# Часть II. Шаги выполнения (строго по порядку)

## Шаг 0. Базовая линия

- Прочитать целиком: `ExpenseController`, `ExpensePolicy`, `PayrollService`,

## Шаг 1. Схема данных: связь выплат с человеком + долги + коды категорий

**Миграции (3 файла):**
1. `expenses`: + `employee_id` (FK users, nullOnDelete, index) +
   `employee_payout` (string 10, nullable) — значения `advance|debt`;
   здесь же индекс `expenses(material_id)` — его нет, а Шаг 11 фильтрует и
   чистит по этой колонке.
   В той же миграции бэкфилл: по `payroll_adjustments.expense_id` →
   `employee_id = user_id`, `employee_payout = 'advance'` (SQL-updateом,
   без загрузки моделей).
2. `employee_debts`: `user_id` FK cascade, `company_id` nullable FK,
   `amount` decimal(15,2), `monthly_payment` decimal(15,2),
   `payment_method` string(4) cash|bank, `expense_id` nullable FK
   nullOnDelete, `note` string nullable, `closed_at` timestamp nullable,
   timestamps. `employee_debt_payments`: `employee_debt_id` FK cascade,
   `month` char(7) 'YYYY-MM', `amount` decimal(15,2), timestamps,
   **unique(employee_debt_id, month)**.
3. `expense_categories`: + `code` string nullable unique. Data-часть:
   `employee` → существующей «Расходы по сотрудникам» (поиск по имени, нет
   — создать), создать «Закуп материалов» с `code='materials_purchase'`.

**Код:**
- Модели `EmployeeDebt` (relations: user, payments, expense; helper
  `balance()` = amount − sum(payments), `isClosed()`), `EmployeeDebtPayment`.
- `ExpenseCategory`: константы `EMPLOYEE='employee'`,
  `MATERIALS_PURCHASE='materials_purchase'`; helper `findByCode()`.
- `ExpenseCategoryController`: категории с `code` нельзя переименовать и
  удалить (серверная проверка + скрыть кнопки в UI со всплывающей
  подсказкой «служебная категория»).
- Создание аванса дополняется `employee_id`/`employee_payout='advance'`.
- `Expense::$fillable` — новые колонки НЕ добавлять в формы; ставит сервер.

**Тесты:** бэкфилл связал старые авансы; кодовую категорию нельзя
переименовать/удалить (403/422); unique(debt, month) отбивает дубль.

**Коммит:** `feat(деньги): выплаты сотрудникам связаны с человеком; таблицы долгов; коды категорий`

## Шаг 2. PayrollService::bonusByUserForMonth (фундамент долгов и плитки ЗП)

- Метод `bonusByUserForMonth(int $userId, string $month): float` — бонус по
  won-сделкам, у которых МЕСЯЦ ПО ДАТЕ ДОГОВОРА = $month (fallback — дата
  создания, ровно как фильтр «Месяц» на Финансах/Сводном — списать правило
  оттуда, не изобретать), считанный существующим `marginBonus` (override и
  личный % работают сами) × доля фактической оплаты. Никаких новых формул.
- Метод используется дальше Шагами 8 и 9 — единственная точка расчёта
  «бонус месяца», второй раз нигде не пересчитывать.

**Тесты:** сделка вне месяца не попадает; override уважается; доля оплаты
уважается; пустой месяц → 0.

**Коммит:** `feat(зп): бонус за месяц по дате договора — единый метод`

## Шаг 3. Права и заморозка расходов

1. `RolePermissionSeeder`: `expense.create` — всем ролям (employee, lawyer,
   cook, designer, supplier; manager уже есть); `expense.delete` УБРАТЬ у
   manager. Плюс разовая data-миграция для прода (сидер там не гоняют):
   вставить недостающие связки, удалить manager→expense.delete.
2. `ExpensePolicy` (роли дублируются в policy — §B.1):
   - `delete`: только `admin|financist` — любые расходы, включая pending
     (менеджер ошибся в материальном списании → просит бухгалтера удалить,
     остаток вернётся, заводит заново);
   - `update`: если `confirmed_by !== null` → только `admin|financist`
     (заморозка; признак — `confirmed_by`, НЕ `status`: материальное
     списание system-confirmed без confirmed_by и для правки НЕ заморожено);
     иначе — автор правит свой pending, чужой pending не-бухгалтер не
     правит.
3. Guard чека: маршрут выдачи файла — автор / `employee_id` / admin,
   director, financist; остальным 403.
4. UI (`FinancePanel`, Финансы): кнопки правки/удаления скрыты по этим же
   правилам; 403-тексты внятные («Расход подтверждён бухгалтером…»,
   «Расходы удаляет бухгалтер или админ.»).

**Тесты:** менеджер не удаляет свой pending; автор не правит после
подтверждения; материальное списание: правка автором возможна, удаление —
только бухгалтер; чек чужой заявки закрыт (IDOR); связка прав восстановлена
миграцией.

**Коммит:** `fix(деньги): удаление расходов только бухгалтер/админ; подтверждённый расход заморожен`

## Шаг 4. Заявка «Расход компании» от любого сотрудника + уведомления потока

1. `ExpenseController::store`, ветка `$entity === null`:
   - `abort_unless(admin|financist)` ЗАМЕНИТЬ на проверку `expense.create`;
   - для НЕ-(admin|financist): принудительно `status='pending'`,
     `payment_method=null` — что бы ни прислали (заявка не двигает кассу;
     откуда платить — решает бухгалтер при подтверждении);
   - admin/financist вводят как раньше (сразу confirmed со способом);
   - категория обязательна (есть), чек можно приложить сразу;
   - **чек-изображение при загрузке ужимать через существующий
     `MediaService` (тот же приём, что фото каталога: до 1600px)** — чеки
     снимают телефоном по 3–8 МБ, а борд Шага 6 показывает их встроенно:
     без сжатия страница бухгалтера станет самой тяжёлой в системе. PDF не
     трогать. Хранение остаётся приватным (`storage/app/private`);
   - менеджерское правило «расход только по своей сделке» ОСТАЁТСЯ для
     расходов по сделке; заявка компании проходит мимо него.
2. Уведомления (по-русски, §A): заявка создана → каждому активному
   admin/financist «Расход компании ждёт проверки» c
   `data.url='/expenses-board'` (страница появится Шагом 6 — маршрут
   зарезервировать константой, чтобы не разъехалось); заявка оплачена →
   автору «Ваш расход оплачен (наличные/банк)» c `data.url='/my-expenses'`.
3. Существующее уведомление «расходы > 60% договора» не трогать.

**Тесты:** цеховой подаёт заявку → pending без способа, бухгалтеры получили
уведомление; менеджер подаёт заявку компании (раньше 403); поле
`payment_method` из формы сотрудника игнорируется; подтверждение шлёт
уведомление автору.

**Коммит:** `feat(деньги): заявка «Расход компании» от любого сотрудника — счёт бухгалтеру`

## Шаг 6. Страница «Расходы» — /expenses-board (рабочее место бухгалтера)

**Backend:** `ExpensesBoardController@index` (admin/director/financist):
- «Требуют проверки»: ВСЕ pending-расходы компании (без фильтра месяца) с
  автором, категорией, чеком; сортировка старые → новые (очередь);
- «Оплаченные за месяц» + фильтр месяца, с пагинацией (за месяц может
  быть сотни записей — очередь pending без пагинации, она короткая);

## Шаг 9. Долги сотрудников

1. Выдача: ЗП → раскрытие сотрудника → «+ выдать долг» → `Modal` (сумма*,
   фиксированный платёж/мес*, нал/банк*, заметка). Создание в транзакции:
   долг + авто-расход confirmed (категория `employee`, `employee_id`,
   `employee_payout='debt'`, способ, дата сегодня) — касса/банк уменьшаются
   сразу. Удаление долга удаляет его расход (и наоборот расход-выдачу
   отдельно удалить нельзя — policy).
2. Команда `debts:charge {--month=}`: default прошлый месяц; в `schedule`
   1-го числа 09:00. По каждому открытому долгу: удержание =
   `min(monthly_payment, bonusByUserForMonth(Шаг 2), balance)`; > 0 →
   insert в `employee_debt_payments` (unique(debt, month) — идемпотентно,
   повторный прогон не спишет второй раз; догнать месяц — `--month=`);
   ТОЛЬКО из бонуса, оклад не трогается: нет бонуса → нет записи, остаток
   переезжает. `balance == 0` → `closed_at = now()`. Транзакция на долг.
3. Ведомость ЗП: у сотрудника с открытым долгом — строка «Долг: остаток X ·
   удержим −Y в этом месяце, останется Z»; «К выплате» − план удержания
   текущего месяца (`debt_charge` — ОТДЕЛЬНОЕ поле расчёта, НЕ в
   deductions: аванс и долг независимы и не гасят друг друга).
4. Модалки аванса и долга — перекрёстные подсказки («Аванс — разовая
   выдача, удерживается целиком в этом месяце из всей выплаты. Долг —
   переходящий, гасится помесячно и только из бонуса.»).
5. Карточка `/users/{id}`: блок долга (таблица погашений) + фильтр месяца в
   шапке блока «Зарплата» — месяц переключает и долг, и корректировки
   (иначе профиль не сходится с ведомостью).

**Тесты:** нет бонуса → нет удержания, остаток переехал; удержание ≤ бонуса
месяца; повторный прогон идемпотентен; `--month` догоняет; закрытие при 0;
выдача уменьшила кассу; удаление долга убрало расход; «К выплате» вычитает
план; аванс и долг не пересекаются.

**Коммит:** `feat(зп): долги сотрудников — выдача из кассы, автогашение только из бонуса`

## Шаг 11a. Бонус за товар со склада — процент от наценки

> Поставлено владельцем 16.08.2026, в исходном плане этого шага не было.
> Опирается на шаг 11: закуп стал денежным событием, а списание — движением
> запаса.

Правило: товар покупают за 10 000 ₸, добавляют свой процент и продают; с
НАЦЕНКИ (продажа − закуп) менеджер сделки получает 2%, когда сделка оплачена.
По складской части ступенчатый бонус от маржи НЕ начисляется — иначе за один
товар платили бы дважды; ступень считается по остальной части сделки.

- Схема: `materials.markup_pct` (пусто — общая наценка из настроек),
  `expenses.sale_amount` — цена продажи, ЗАФИКСИРОВАННАЯ при списании.
- Настройки: `material_markup_percent` (общая наценка) и
  `warehouse_bonus_percent` (ставка бонуса, по умолчанию 2).
- `PayrollService::dealBonus` — единая точка расчёта бонуса по сделке
  (ступень + складская часть); все семь мест расчёта переведены на неё.
- Правило включается только при наличии наценки (`sale_amount > amount`):
  старые списания и товар без наценки остаются в обычном бонусе целиком.

**Коммит:** `feat(зп): бонус менеджера за товар со склада — процент от наценки`

## Шаг 12. Целостность денег + итог без двойного счёта ЗП

1. Платёж ≤ остатка счёта: `PaymentController::store` — транзакция,

2. Анти-дубль поступлений и расходов: идентичная запись того же автора
   (сумма+дата+описание) младше 1 минуты → ValidationException «Похоже на
   повторную отправку — запись уже создана.»
3. «В работу ✓» заявки → сделка: транзакция + `lockForUpdate` по заявке
   (двойной клик давал 2 сделки в BAIA; у нас тот же перенос — проверить и
   закрыть; уникальность номера сделки не спасает от гонки generate).
4. Дебиторка не считает отменённые счета — проверить скоуп
   `FinanceService`, закрыть тестом.
5. Итог «Расходы» на Финансах и Аналитике ИСКЛЮЧАЕТ категорию `employee`
   (зарплата присутствует строкой payrollTotal — иначе двойной счёт); в
   разбивке категория видна с пометкой «учтено в строке „Зарплата“»;
   кассу/банк такие расходы уменьшают честно (НЕ трогать). Выплата ЗП =
   расход этой категории — касса сходится, итог не задваивается.

6. **Команда `finance:selfcheck`** — сквозная проверка инвариантов на
   ЖИВЫХ данных: касса/банк из `FinanceService` == пересчёт с нуля по
   платежам/поступлениям/расходам; дебиторка == счета − платежи (без
   отменённых); сумма секций ЗП == плитке «К выплате»; книга дня стыкуется
   день-в-день. Вывод — таблица «инвариант / ожидание / факт / расхождение».

   цифр; баг или ручная правка в БД должны находиться командой за минуту, а
   не спором «какая страница врёт». Запускается вручную и в конце сидера
   тестов.

**Тесты:** на каждый из пяти пунктов, включая двойной клик (два
последовательных POST) и сходимость: Финансы == Аналитика == кассовая книга

**Коммит:** `fix(деньги): переплата счёта, дубли, гонка «В работу», дебиторка, двойной счёт ЗП`

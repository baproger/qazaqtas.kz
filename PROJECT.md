# QAZAQ TAS ERP / CRM — Документация проекта

> Единый файл-справочник: суть проекта, что построено, как работает логика.
> ⚠️ **Если репозиторий публичный** — здесь и в коде НЕТ логинов, паролей, ключей и реальных данных. Все доступы (`.env`, БД, `APP_KEY`, FTP, учётки) хранятся ТОЛЬКО на сервере и у владельца.

## 0. Суть проекта

**QAZAQ TAS ERP** — внутренняя ERP/CRM производства малых архитектурных форм (МАФ) и тротуарной плитки из **мраморного композита**: вазоны, скамьи, урны, фонтаны, бордюры, облицовка, плитка. Заменяет Excel отдела продаж и тетради бухгалтерии. Система построена на форке BAIA ERP и адаптирована под прямые B2B/B2C-заказы.

Жизненный цикл денег и заказа:
1. **Заявка / запрос КП** — менеджер вносит объём (м²/шт), цену за единицу и себестоимость; система считает маржу. Маржа ≥ порога (15%) → «В работу ✓» → создаётся сделка.
2. **Сделка** идёт по воронке: Заявка → Замер и расчёт (гейт технолога) → Договор → Закуп сырья (гейт снабженца) → «В цех».
3. **Цех**: производство в трёх городах — **Шымкент, Алматы, Тараз**; менеджер выбирает площадку при отправке. Заказ идёт по этапам своего цеха с таймингом каждого этапа — Формовка → Шлифовка → Упаковка → Отправка; «Готово ✓» возвращает сделку на Логистику.
4. Логистика → Монтаж → Акт → ЭСФ → **Оплата успешно** (двигает только бухгалтер).
5. **Финансы**: счета, платежи, расходы (по сделкам и компании), поступления, касса/банк, дебиторка. **ЗП**: оклад + ступенчатый бонус от маржи. **Аналитика/Сводный отчёт** — для руководства. **ТВ-экраны** в цехе и офисе — живые канбаны/рейтинги по коду доступа.

## 1. Технологии
- **Backend:** Laravel 13 (прод PHP 8.3 — composer.json `config.platform.php=8.3.30`), MySQL
- **Frontend:** Inertia.js + Vue 3 + Tailwind + Vite (Laravel Breeze); на витрине — Three.js, GSAP ScrollTrigger и Lenis (грузятся отдельными чанками только на страницах с 3D)
- **Права:** spatie/laravel-permission (RBAC). **Admin — глобальный суперпользователь** (Gate::before). Роль admin назначает только admin; последний активный админ защищён от разжалования/деактивации.
- **Таймзона:** Asia/Almaty (+05:00); **Локализация:** ru / kk
- **Тесты:** PHPUnit — 298, все зелёные. Перед каждым push: `npm run build` + `php artisan test`.
- **Продакшн (Plesk):** сессии/кэш — файлы, очередь — sync; `public/build/` закоммичен, а `vendor/` — НЕТ: его пересобирает деплой командой `php composer.phar install --no-dev`; деплой — см. `DEPLOY.md`.

## 2. Роли и доступы
| Роль | Что видит / может |
|------|-----------|
| **admin** (СЕО) | всё; только он удаляет сделки и назначает роль admin |
| **director** | всё как наблюдатель; этапы АКТ/ЭСФ/Оплата не двигает |
| **financist** (Финансист-Бухгалтер) | финансы, аналитика, ЗП, создание сделок, сотрудники (кроме админов), категории расходов, чек-лист заявок, план продаж |
| **manager** | ТОЛЬКО свои сделки/заявки/цех/финансы/бонус; общей аналитики не видит |
| **employee (цех)** | карточки цеха (двигает этапы), свои задачи; суммы не видит |
| **lawyer / cook** | уровень «сотрудник»: цех, задачи, своя ЗП |
| **designer (Технолог) / supplier (Снабженец)** | как сотрудник + сделки: в списках видят ТОЛЬКО сделки своего гейт-этапа (design/shop_gate), по прямой ссылке — любую сделку компании; при входе сделки на их этап — задача+уведомление, без их галочки сделка дальше не идёт |

## 3. Модули
- **Заявки (/pre-deals):** запросы КП как Excel отдела продаж — № заявки, срок действия КП, заказчик, БИН/ИИН, объект (адрес монтажа), изделие, объём + единица (м²/шт/паллета…), цена за единицу, себестоимость, партнёр %, доставка, монтаж, комиссия. **Сумма КП = объём × цена** (считается автоматически; если объём не задан — вводится вручную). Авто-расчёт (`PreDeal::calculate`): партнёр = %×сумма, налог = ставка×сумма, остаток = сумма−всё, маржа = остаток/сумма (живой расчёт и в форме). Маржа ≥ порога (Setting `predeal_min_margin`, 15%) → кнопка «В работу ✓» создаёт сделку и переносит доставку/монтаж в её расходы; ниже — «отклонена» (сервер блокирует). Откат ↩ возможен, пока по сделке нет счетов/расходов/заказа цеха. Менеджер видит только свои; руководство — все + фильтры + «Рейтинг менеджеров» (👑). Чек-лист заявки (`pre_deal_checklist_items`: «Позвонил клиенту», «Сделал замер объекта», «Отправил КП», «Согласовал образец и цвет») — галочки в раскрытой строке; пункты настраивают admin/financist («⚙ Чек-лист»). Срок КП: в день истечения менеджеру приходит напоминание (`pre-deals:notify-quote-deadline`, 09:00).
- **Сделки:** канбан+список; **история этапов** (deal_stage_logs): ⏱ на карточке канбана + «Тайминг этапов» во вкладке «История» (когда вошла/ушла, сколько заняло, кто перевёл); фильтр-бар (поиск, менеджер, этап, срок/договор с—по); карточка с вкладками (Задачи/Финансы/Документы/Комментарии/Доп.поля/История/Чат). Поля: клиент, адрес объекта, № договора, дата договора, канал продаж (Сайт/Instagram/WhatsApp/звонок/рекомендация/выставка/дилер/госзакуп), изделие, кол-во + ед. изм. (м², м³, шт, п.м., паллета, тонна, кг, мешок, литр, рулон), сумма, срок, заметка. Доп-поля из коробки: тип изделия, цвет/пигмент, фактура поверхности.
- **Цех (Projects):** канбан секциями по городам — **Шымкент, Алматы, Тараз**; у каждого своя воронка (Формовка → Шлифовка → Упаковка → Отправка), свой ТВ-экран и свой состав сотрудников. При «Отправить в цех» менеджер выбирает город (без выбора сервер не пропустит). **Доступ сотрудников по цехам** (`users.workshops`, форма сотрудника → «Доступ к цехам»): работник Шымкента видит и двигает только свои заказы (403 и по прямой ссылке), можно отметить несколько городов; пусто = все цеха (руководство). Новый цех добавляется в Настройки → Этапы (вид «цех», поле «Цех») — код менять не нужно. **Тайминг этапов** (project_stage_logs): бейдж «⏱ Nч Nм» на карточках + история этапов на карточке заказа. Суммы от цеха скрыты.
- **ТВ-экраны (/screen, без логина, вход по 6-значному коду):** управление — Настройки → Экраны (коды по цехам + строка «Офис», копирование кода, вкл/выкл, «Новый код» отключает старые; throttle 10/мин). **Экран цеха** — свой код на каждый город, светлый канбан только своего цеха (без сумм, тайминг, часы, автообновление 10с); «Далее →» двигает заказ, на последнем этапе («Отправка») — «Готово ✓ — в Логистику» (единая логика ERP/экрана — `ProjectService::completeAndReturnDeal`). **Экран «Офис»** — воронка отдела крупными цифрами: Заявки → каждый пункт чек-листа → В работе, у каждой плитки факт/план (`sales_plan_monthly`, `sales_plan_won_monthly`); рейтинг менеджеров по заявкам с персональными воронками и автопрокруткой; таблица «Заявки месяца — чек-листы»; деньги не показываются; фильтр месяца; автообновление 10с.
- **Склад:** свой у каждой фирмы; приход (admin/financist) с ценой закупки; таблица материал/ед/цена/поступление/сумма/списание (кликабельно) /остаток; материальный расход в сделке = кол-во × закупочная цена (авто, confirmed сразу, списывает остаток). Стартовая номенклатура (`MaterialSeeder`): мраморная крошка (0–2, 2–5 мм), мраморная мука, цемент белый/серый, полиэфирная смола, отвердитель, гелькоут, пигменты, пластификатор, гидрофобизатор, разделительная смазка, фиброволокно, арматура, полиуретановые формы, шлифовальные круги, стрейч-плёнка, паллеты.
- **Финансы:** первым блоком **ДДС** — ручная Excel-сводка (dds_entries, БЕЗ связей с расчётами): счета компаний (банк/фактический остаток/дебиторский) + долги + дата. **Счета**: сегодняшние сверху + прошлые аккордеоном, колонка «Сделка», статусы по-русски. Платежи, расходы сделок с ВИДАМИ — 🚚 доставка / 📦 закуп / прочие / материалы со склада (pending → бухгалтер подтверждает с чеком и нал/банк) и расходы КОМПАНИИ по категориям («⚙ Категории»; из коробки: аренда, комуслуги, электроэнергия, интернет, ГСМ, сырьё и материалы, формы и оснастка, ремонт оборудования, доставка и логистика, реклама, канцтовары, хозтовары, продукты, офис, налоги, кредит, прочее). Поступления денег (нал/банк, откуда) — сегодня + аккордеон прошлых; касса/банк = поступило − потрачено по способу оплаты (**касса — ЕДИНАЯ на все фирмы**, **банк — раздельно**; **корректировка кассы** — ✎, только админ, пишется в Setting `cash_correction` и в аудит); дебиторка (авто по счетам + вручную); удаление любой финзаписи → уведомление СЕО и директору; «Доход» = итог Сводного отчёта; селектор «Месяц» пересчитывает Доход/Оборот/Расходы/Итог. Расходы > 60% суммы договора → уведомление финансистам (однократно).
- **Зарплата:** видны ВСЕ активные сотрудники. К выплате = оклад + бонус − удержания + премии за месяц; корректировки (отгул/больничный днями = оклад/22×дни, штраф, аванс, премия) вводит financist/admin; **аванс** = реальные деньги: выбирается нал/банк, автоматически создаётся подтверждённый расход «Расходы по сотрудникам» (уменьшает кассу/банк), удаление аванса удаляет и расход; бонус ступенчатый от маржи каждой won-сделки × доля фактической оплаты (min(1, paid/budget)).
- **Аналитика (руководство):** LIVE-режим (часы, автообновление 60с), SVG-диаграмма доход/расход по месяцам, донат по статусам, спидометр конверсии, воронка, топ менеджеров, ABC, разбивка расходов сделок по видам, «требует внимания», «Деньги компании» (единая математика с Финансами через PayrollService/FinanceService). Вкладка «По сотрудникам»: рейтинг с местами, шкала ЗП к лидеру, плитки показателей.
- **Сводный отчет** (admin/director): Excel-таблица всех сделок + цеха (закуп-склад / 🚚 доставка / 📦 закуп / прочие — раздельно, налог/остаток/маржа/бонус/доход); фильтр сотрудника; период фильтрует по дате договора.
- **Чат:** мессенджер (группы, файлы, цитаты, правка, реакции, закреп, @упоминания, счётчики непрочитанных, архив, корзина, участники); чат сделки привязан к deal_id; группы по фирмам; звук новых сообщений; «кто прочитал» ✓✓; веб-пуш через `public/sw.js`.
- **Сотрудники (HR) + Отделы:** карточки по отделам (Отдел продаж, Производство — Шымкент / Алматы / Тараз, Снабжение, Логистика и монтаж, Бухгалтерия), живой поиск, фильтр-чипы, мини-статистика; у отделов руководитель (⭐, получает уведомления о просроченных задачах отдела и днях рождения). Поля: день рождения (🎂 ≤7 дн., `users:notify-birthdays` 09:00), дата приёма (стаж), доступ к цехам, договор-файл. **Профиль /users/{id}**: контакты, показатели, ЗП-расчёт + корректировки, сделки/заказы цеха/задачи. Экспорт CSV.
- **Аудит (admin):** фильтры (раздел/действие/пользователь/период), всё по-русски, ссылка на запись, IP; фиксируются корректировка кассы и строки ДДС.
- **Просроченные:** сделки (без ЭСФ/won; Акт — считается) + отдельно заказы цеха. **Задачи, Документы, Уведомления, Доп.поля, Настройки (Общие/Этапы/Экраны/Доп.поля), Переводы.**
- Порядок меню: Аналитика → Просроченные → Заявки → Заказы с сайта → Сделки → Цех → Склад → Каталог сайта → Сводный отчет → Финансы → Зарплата → Чат → … → Сотрудники → Профиль → Настройки.

## 3a. Публичный сайт и интернет-магазин

Витрина живёт в том же приложении (Inertia + Vue), на публичных маршрутах
(`routes/site.php`) и **читает каталог прямо из ERP** — отдельной базы товаров
и отдельной админки нет.

- **Адреса:** `/` — главная, `/katalog`, `/katalog/{slug}` — карточка,
  `/konfigurator`, `/korzina`, `/oformlenie`, `/zavod`, `/proekty`, `/kontakty`.
  ERP осталась на своих адресах (`/login`, `/dashboard`, `/deals`…).
- **Дизайн:** тёмная «бетонная» тема (`.site` в `resources/css/app.css`):
  крупная типографика, стекло (`.glass`), зерно и виньетки, песочный акцент
  мраморного композита. ERP по-прежнему светлая — темы не пересекаются.
- **Главная — гибрид 3D и фотографий:** сначала 3D-сборка двора при скролле
  (технология), затем **полноэкранные кадры реальных объектов** — снимки
  «прилипают» на весь экран, медленно отъезжает масштаб, поверх идут город,
  год, состав и объём. В историю попадают только объекты с фотографией;
  нет фото — секция просто не показывается.
- **Объекты сайта** (ERP → «Объекты сайта», таблица `site_projects`,
  ведут admin/director/financist): название, город, год, объём, состав,
  описание и фотография (ужимается тем же `MediaService`). Стартовый набор из
  `SiteContent::projects()` подставляется, только пока таблица пуста — если
  объекты заведены и скрыты, это решение владельца, витрина его не подменяет.
- **3D-история на главной:** Three.js собирает двор по мере скролла (одна
  плитка → раскладка → бордюры → скамья, вазоны, урна → общий план).
  Геометрия процедурная, GSAP ScrollTrigger отдаёт прогресс, Lenis сглаживает
  скролл. Освещение — IBL через `PMREMGenerator` + `RoomEnvironment` (без
  внешних HDRI-файлов) плюс ACES-тонемаппинг и мягкие тени: материалы читаются
  как бетон, а не как пластик. Сцена грузится отдельным чанком и только при подходе к секции,
  простаивает вне экрана и уважает `prefers-reduced-motion`.
- **3D-конфигуратор двора** (`/konfigurator`): коллекция плитки, цвет,
  раскладка (со смещением / шов в шов / ёлочка / плетёнка), размеры участка,
  бордюр по периметру и малые формы. Сцена — InstancedMesh с орбитальным
  управлением; количество, запас на подрезку и стоимость считаются по
  `specs.pieces_per_m2` и ценам каталога. Итог уходит в корзину или в WhatsApp.
- **Каталог:** категории, поиск, фильтр по цене, сортировка, избранное,
  сравнение и «недавно смотрели» (localStorage), похожие товары, характеристики,
  документы. Пока в карточке ERP нет фото, превью рисуется вектором по типу
  изделия и выбранному цвету (`ProductVisual.vue`).
- **Покупка:** корзина в сессии (цены всегда из ERP), калькулятор площади,
  калькулятор бордюра, прикидка доставки по городу, оформление заказа и
  заказ в WhatsApp одной кнопкой.
- **Заказы:** `orders` + `order_items`, номер `ZT-2026-0001`. Заказ сразу виден
  в ERP («Заказы с сайта»), менеджеры и руководство получают уведомление,
  кнопка «В сделку» создаёт сделку через `DealNumberService` на первом этапе
  обычной воронки — состав заказа уходит в описание.
- **Контент** (контакты, филиалы, цифры, этапы производства, преимущества,
  FAQ, проекты, тарифы доставки) — `App\Support\SiteContent`: значения по
  умолчанию перекрываются настройками ERP, отдельной CMS нет.
- **Каталог в ERP** (`/catalog`, права `product.*`): карточки, категории,
  характеристики «ключ: значение», палитра «Название #HEX», публикация,
  «на главной», «в наличии». Кэш витрины сбрасывается при каждом сохранении.
  ERP-маршруты каталога работают по `id` (slug меняется вместе с названием).
- **Медиа карточки** (вкладка «Фото, 3D и документы»): загрузка фото
  (`MediaService` ужимает до 1600 px + превью 600 px, витрина отдаёт srcset),
  выбор главного снимка, **привязка снимка к цвету изделия** (выбор цвета в
  карточке переключает галерею на фото этого цвета; снимки без привязки видны
  всегда, а если фото нужного цвета нет — витрина честно пишет об этом),
  документы (паспорт, сертификат, схема укладки) и
  необязательная 3D-модель. Кнопка **3D** помечает фото как ТЕКСТУРУ:
  этим снимком 3D-сцена главной и конфигуратор красят изделие вместо ровного
  цвета (`CatalogService::sceneAssets()`), а GLB-модель заменяет процедурную
  геометрию скамьи и вазона. Лучший исходник для текстуры — фрагмент
  поверхности сверху при ровном свете.
- **Форматы 3D:** **GLB/GLTF** — один самодостаточный файл (предпочтительно);
  **OBJ** — комплектом `.obj` + `.mtl` + текстуры одной загрузкой: `.mtl`
  ссылается на файлы по именам, поэтому комплект кладётся в общую папку
  `catalog/{id}/models` с сохранёнными именами (`MediaService::storeModelSet`).
  OBJ без `.mtl` загрузится, но изделие будет серым — интерфейс об этом
  предупреждает. Загрузчик витрины (`resources/js/site/gltf.js`) выбирает
  GLTFLoader или OBJLoader+MTLLoader по расширению; при ошибке возвращает null,
  и сцена рисует процедурную геометрию.


## 4. Логика денег (единые формулы)
- **По сделке:** налог = бюджет × ставка (Setting `tax_percent`, 3%); остаток = бюджет − налог − confirmed-расходы; маржа % = (бюджет − расходы)/бюджет (ДО налога — по ней ступень бонуса); бонус = ставка(маржа) × остаток × min(1, оплачено/бюджет); **ручной % бонуса** по сделке (`deals.bonus_rate_override`, ставит financist/admin) перекрывает ступени ВО ВСЕХ расчётах (единый `PayrollService::marginBonus`).
- **Ступени бонуса:** ≤10%→0; 11–15→5%; 16–20→7%; 21–30→10%; 31–40→13%; ≥41→15% (`PayrollService::bonusRateForMargin`).
- **Доход компании** = фактические платежи по won-сделкам; **расход** — все confirmed сразу; «Доход (Сводный отчёт)» = Σ(остаток − бонус) по не-отменённым сделкам. Один источник правды: PayrollService (companyTotals/perUser/dealBreakdown) + FinanceService (companyBalances/dealsIncome).

## 5. Ключевые бизнес-правила
- **Мультикомпанийность:** сейчас одна фирма — **QAZAQ TAS (код QT)**, номера сделок `QT-001`. Механизм фирм в коде сохранён: вторая фирма заводится строкой в `companies` (+ своя воронка в Настройки → Этапы), данные изолируются политиками (`worksInCompany`), режим «Все» — сводно.
- **Спец-этапы по stage_type** (contract/design/shop_gate/logistics/assembly/act/esf/payment_won) — переименование не ломает логику; тип уникален в воронке.
- **Гейт-задачи этапов:** текст/роль/срок на этапе; при входе — задача каждому активному сотруднику роли + уведомление; сделка дальше не идёт, пока не закрыта. Из коробки: «Замер и расчёт» → технолог (3 дня), «Закуп сырья» → снабженец (5 дней), «Акт утверждение» → бухгалтер (3 дня).
- **Роли по этапам:** менеджер до Акта; АКТ/ЭСФ/Оплата — только financist/admin; после Акта менеджеру read-only. Оплата успешно НЕ требует полной оплаты (остаток — в дебиторку). Удаление сделок — только admin (+bulk); каскад: заказ цеха отменяется, ссылки помечаются «сделка удалена».
- **Нумерация сделок:** `QT-001` по фирме; считаются только ЖИВЫЕ (при удалении номер освобождается: `…#del{id}`); удалили все — снова с 001.
- Счёт с суммой 0 запрещён; статусы счетов — только пересчётом платежей; расход/счёт не переставить на чужую сделку.
- Просрочка: ЭСФ/won исключены, Акт — просрочен; и сделки, и заказы цеха.

## 6. Скорость и безопасность
- **Перф:** OPcache на проде обязателен; после каждого деплоя `php artisan optimize`; индексы под горячие запросы; чат/экраны не поллят из фоновых вкладок; статика с `Cache-Control: immutable, 1y`; код-сплит по страницам.
- **Безопасность:** SecureHeaders (nosniff, X-Frame-Options, Referrer-Policy, Permissions-Policy, HSTS), принудительный HTTPS в production, троттлинг логина и публичных форм, скрытые файлы в `public/` не отдаются (403), прод `.env`: `APP_DEBUG=false`, `SESSION_SECURE_COOKIE=true`. Аудит-лог, уведомления об удалении финзаписей. Рекомендовано: регулярные бэкапы БД, ротация паролей после любых передач.

# QAZAQ TAS ERP / CRM — Документация проекта

> Единый файл-справочник: суть проекта, что построено, как работает логика.
> ⚠️ **Если репозиторий публичный** — здесь и в коде НЕТ логинов, паролей, ключей и реальных данных. Все доступы (`.env`, БД, `APP_KEY`, FTP, учётки) хранятся ТОЛЬКО на сервере и у владельца.

## 0. Суть проекта

**QAZAQ TAS ERP** — внутренняя ERP/CRM производства малых архитектурных форм (МАФ) и тротуарной плитки из **мраморного композита**: вазоны, скамьи, урны, фонтаны, бордюры, облицовка, плитка. Заменяет Excel отдела продаж и тетради бухгалтерии. Система построена на форке BAIA ERP и адаптирована под прямые B2B/B2C-заказы.

Жизненный цикл денег и заказа:
1. **Заявка / запрос КП** — менеджер вносит объём (м²/шт), цену за единицу и себестоимость; система считает маржу. Маржа ≥ порога (15%) → «В работу ✓» → создаётся сделка.
2. **Сделка** идёт по воронке: Заявка → Замер и расчёт (гейт технолога) → Договор → Закуп сырья (гейт снабженца) → «В цех».
3. **Цех**: производство в трёх городах — **Шымкент, Алматы, Тараз**; менеджер выбирает площадку при отправке. Заказ идёт по этапам своего цеха с таймингом каждого этапа — Формовка → Шлифовка → Упаковка → Отправка; «Готово ✓» возвращает сделку на Логистику.
4. Логистика → Монтаж → Акт → ЭСФ → **Оплата успешно** (двигает только бухгалтер).
5. **Финансы**: счета, платежи, расходы (по сделкам и компании), поступления, касса/банк, дебиторка. **ЗП**: оклад + ступенчатый бонус от маржи. **Аналитика/Сводный отчёт** — для руководства. **ТВ-экраны** в цехе и офисе — живые канбаны/рейтинги по коду доступа.

## 1. Технологии
- **Backend:** Laravel 13 (прод PHP 8.3 — composer.json `config.platform.php=8.3.30`), MySQL
- **Frontend:** Inertia.js + Vue 3 + Tailwind + Vite (Laravel Breeze); на витрине — Three.js, GSAP ScrollTrigger и Lenis (грузятся отдельными чанками только на страницах с 3D)
- **Права:** spatie/laravel-permission (RBAC). **Admin — глобальный суперпользователь** (Gate::before). Роль admin назначает только admin; последний активный админ защищён от разжалования/деактивации.
- **Таймзона:** Asia/Almaty (+05:00); **Языки:** казахский (основной) и русский — см. раздел 3b.
- **Стили витрины** разложены по слоям: `tokens.css` (палитры дня и ночи), `surfaces.css` (полотно, `.card`, кнопки), `site.css` (панели, лента, кнопка связи, подвал), `hero.css` (витрина изделий). `app.css` только собирает их; `postcss-import` раскрывает `@import` до Tailwind — иначе `@apply` в слоях остаётся необработанным.
- **Тесты:** PHPUnit — 369, все зелёные. Перед каждым push: `npm run build` + `php artisan test`.
- **CI:** GitHub Actions на каждый push и PR — `composer audit`, `php artisan test`, `npm run build`; собранный фронт сохраняется артефактом `build`.
- **Продакшн (Plesk):** сессии/кэш — файлы, очередь — sync. `public/build/` и `vendor/` в git НЕ хранятся: фронт приезжает артефактом CI либо собирается на сервере (`npm ci && npm run build`), зависимости — `php composer.phar install --no-dev`; деплой — см. `DEPLOY.md`.

## 2. Роли и доступы
| Роль | Что видит / может |
|------|-----------|
| **admin** (СЕО) | всё; только он удаляет сделки и назначает роль admin |
| **director** | всё как наблюдатель; этапы АКТ/ЭСФ/Оплата не двигает |
| **financist** (Финансист-Бухгалтер) | финансы, аналитика, ЗП, создание сделок, сотрудники (кроме админов), категории расходов, чек-лист заявок, план продаж |
| **manager** | ТОЛЬКО свои сделки/заявки/цех/финансы/бонус; общей аналитики не видит |
| **employee (цех)** | карточки цеха (двигает этапы), свои задачи; суммы не видит |
| **lawyer / cook** | уровень «сотрудник»: цех, задачи, своя ЗП |
| **designer (Технолог) / supplier (Снабженец)** | как сотрудник + сделки: в списках видят ТОЛЬКО сделки своего гейт-этапа (design/shop_gate), по прямой ссылке — любую сделку компании; при входе сделки на их этап — задача+уведомление, без их галочки сделка дальше не идёт |

## 3. Модули
- **Заявки (/pre-deals):** запросы КП как Excel отдела продаж — № заявки, срок действия КП, заказчик, БИН/ИИН, объект (адрес монтажа), изделие, объём + единица (м²/шт/паллета…), цена за единицу, себестоимость, партнёр %, доставка, монтаж, комиссия. **Сумма КП = объём × цена** (считается автоматически; если объём не задан — вводится вручную). Авто-расчёт (`PreDeal::calculate`): партнёр = %×сумма, налог = ставка×сумма, остаток = сумма−всё, маржа = остаток/сумма (живой расчёт и в форме). Маржа ≥ порога (Setting `predeal_min_margin`, 15%) → кнопка «В работу ✓» создаёт сделку и переносит доставку/монтаж в её расходы; ниже — «отклонена» (сервер блокирует). Откат ↩ возможен, пока по сделке нет счетов/расходов/заказа цеха. Менеджер видит только свои; руководство — все + фильтры + «Рейтинг менеджеров» (👑). Чек-лист заявки (`pre_deal_checklist_items`: «Позвонил клиенту», «Сделал замер объекта», «Отправил КП», «Согласовал образец и цвет») — галочки в раскрытой строке; пункты настраивают admin/financist («⚙ Чек-лист»). Срок КП: в день истечения менеджеру приходит напоминание (`pre-deals:notify-quote-deadline`, 09:00).
- **Сделки:** канбан+список; **вкладки филиалов** над списком (Все · Шымкент ·
  Алматы · Тараз) со счётчиками — работают и в канбане, и в списке, вместе с
  поиском и остальными фильтрами. Счётчики считаются БЕЗ учёта выбранной
  вкладки: иначе, открыв Шымкент, руководитель видел бы нули у остальных и не
  понимал, куда переключаться. «Без филиала» — отдельная вкладка, а не пустота:
  сделки без назначенной площадки иначе не попадали бы никуда и терялись из
  виду; вкладка появляется только когда такие сделки есть. Отбор сделок и
  счётчики считаются одним методом (`DealController::filteredDeals`) —
  разойдись они, цифра на вкладке перестала бы сходиться с её содержимым.
  Филиал правится прямо в карточке сделки (раньше его задавали только при
  создании, и ошибку выбора нечем было исправить). У сделки также **площадь м²**
  рядом с количеством и **товар из каталога** (выбор подставляет название и единицу, поле можно поправить руками); **история этапов** (deal_stage_logs): ⏱ на карточке канбана + «Тайминг этапов» во вкладке «История» (когда вошла/ушла, сколько заняло, кто перевёл); фильтр-бар (поиск, менеджер, этап, срок/договор с—по); карточка с вкладками (Задачи/Финансы/Документы/Комментарии/Доп.поля/История/Чат). Поля: клиент, адрес объекта, № договора, дата договора, канал продаж (Сайт/Instagram/WhatsApp/звонок/рекомендация/выставка/дилер/госзакуп), изделие, кол-во + ед. изм. (м², м³, шт, п.м., паллета, тонна, кг, мешок, литр, рулон), сумма, срок, заметка. Доп-поля из коробки: тип изделия, цвет/пигмент, фактура поверхности.
- **Цех (Projects):** канбан секциями по городам — **Шымкент, Алматы, Тараз**; у каждого своя воронка (Формовка → Шлифовка → Упаковка → Отправка), свой ТВ-экран и свой состав сотрудников. При «Отправить в цех» менеджер выбирает город (без выбора сервер не пропустит). **Доступ сотрудников по цехам** (`users.workshops`, форма сотрудника → «Доступ к цехам»): работник Шымкента видит и двигает только свои заказы (403 и по прямой ссылке), можно отметить несколько городов; пусто = все цеха (руководство). Новый цех добавляется в Настройки → Этапы (вид «цех», поле «Цех») — код менять не нужно. **Тайминг этапов** (project_stage_logs): бейдж «⏱ Nч Nм» на карточках + история этапов на карточке заказа. Суммы от цеха скрыты.
- **ТВ-экраны (/screen, без логина, вход по 6-значному коду):** управление — Настройки → Экраны (коды по цехам + строка «Офис», копирование кода, вкл/выкл, «Новый код» отключает старые; throttle 10/мин). **Экран цеха** — свой код на каждый город, светлый канбан только своего цеха (без сумм, тайминг, часы, автообновление 10с); «Далее →» двигает заказ, на последнем этапе («Отправка») — «Готово ✓ — в Логистику» (единая логика ERP/экрана — `ProjectService::completeAndReturnDeal`). **Экран «Офис»** — воронка отдела крупными цифрами: Заявки → каждый пункт чек-листа → В работе, у каждой плитки факт/план (`sales_plan_monthly`, `sales_plan_won_monthly`); рейтинг менеджеров по заявкам с персональными воронками и автопрокруткой; таблица «Заявки месяца — чек-листы»; деньги не показываются; фильтр месяца; автообновление 10с.
- **Склад:** свой у каждой фирмы; приход (admin/financist) с ценой закупки; таблица материал/ед/цена/поступление/сумма/списание (кликабельно) /остаток; материальный расход в сделке = кол-во × закупочная цена (авто, confirmed сразу, списывает остаток). Стартовая номенклатура (`MaterialSeeder`): мраморная крошка (0–2, 2–5 мм), мраморная мука, цемент белый/серый, полиэфирная смола, отвердитель, гелькоут, пигменты, пластификатор, гидрофобизатор, разделительная смазка, фиброволокно, арматура, полиуретановые формы, шлифовальные круги, стрейч-плёнка, паллеты.
- **Финансы:** первым блоком **ДДС** — ручная Excel-сводка (dds_entries, БЕЗ связей с расчётами): счета компаний (банк/фактический остаток/дебиторский) + долги + дата. **Счета**: сегодняшние сверху + прошлые аккордеоном, колонка «Сделка», статусы по-русски. Платежи, расходы сделок с ВИДАМИ — 🚚 доставка / 📦 закуп / прочие / материалы со склада (pending → бухгалтер подтверждает с чеком и нал/банк) и расходы КОМПАНИИ по категориям («⚙ Категории»; из коробки: аренда, комуслуги, электроэнергия, интернет, ГСМ, сырьё и материалы, формы и оснастка, ремонт оборудования, доставка и логистика, реклама, канцтовары, хозтовары, продукты, офис, налоги, кредит, прочее). Поступления денег (нал/банк, откуда) — сегодня + аккордеон прошлых; касса/банк = поступило − потрачено по способу оплаты (**касса — ЕДИНАЯ на все фирмы**, **банк — раздельно**; **корректировка кассы** — ✎, только админ, пишется в Setting `cash_correction` и в аудит); дебиторка (авто по счетам + вручную); удаление любой финзаписи → уведомление СЕО и директору; «Доход» = итог Сводного отчёта; селектор «Месяц» пересчитывает Доход/Оборот/Расходы/Итог. Расходы > 60% суммы договора → уведомление финансистам (однократно).
- **Зарплата:** видны ВСЕ активные сотрудники. К выплате = оклад + бонус − удержания + премии за месяц; корректировки (отгул/больничный днями = оклад/22×дни, штраф, аванс, премия) вводит financist/admin; **аванс** = реальные деньги: выбирается нал/банк, автоматически создаётся подтверждённый расход «Расходы по сотрудникам» (уменьшает кассу/банк), удаление аванса удаляет и расход; бонус ступенчатый от маржи каждой won-сделки × доля фактической оплаты (min(1, paid/budget)).
- **Аналитика (руководство):** LIVE-режим (часы, автообновление 60с), SVG-диаграмма доход/расход по месяцам, донат по статусам, спидометр конверсии, воронка, топ менеджеров, ABC, разбивка расходов сделок по видам, «требует внимания», «Деньги компании» (единая математика с Финансами через PayrollService/FinanceService). Вкладка «По сотрудникам»: рейтинг с местами, шкала ЗП к лидеру, плитки показателей.
- **Сводный отчет** (admin/director): Excel-таблица всех сделок + цеха (закуп-склад / 🚚 доставка / 📦 закуп / прочие — раздельно, налог/остаток/маржа/бонус/доход); фильтр сотрудника; период фильтрует по дате договора.
- **Чат:** мессенджер (группы, файлы, цитаты, правка, реакции, закреп, @упоминания, счётчики непрочитанных, архив, корзина, участники); чат сделки привязан к deal_id; группы по фирмам; звук новых сообщений; «кто прочитал» ✓✓; веб-пуш через `public/sw.js`.
- **Сотрудники (HR) + Отделы:** карточки по отделам (Отдел продаж, Производство — Шымкент / Алматы / Тараз, Снабжение, Логистика и монтаж, Бухгалтерия), живой поиск, фильтр-чипы, мини-статистика; у отделов руководитель (⭐, получает уведомления о просроченных задачах отдела и днях рождения). Поля: день рождения (🎂 ≤7 дн., `users:notify-birthdays` 09:00), дата приёма (стаж), доступ к цехам, договор-файл. **Профиль /users/{id}**: контакты, показатели, ЗП-расчёт + корректировки, сделки/заказы цеха/задачи. Экспорт CSV.
- **Аудит (admin):** фильтры (раздел/действие/пользователь/период), всё по-русски, ссылка на запись, IP; фиксируются корректировка кассы и строки ДДС.
- **Просроченные:** сделки (без ЭСФ/won; Акт — считается) + отдельно заказы цеха. **Задачи, Документы, Уведомления, Доп.поля, Настройки (Общие/Этапы/Экраны/Доп.поля), Переводы.**
- Порядок меню: Аналитика → Просроченные → Заявки → Заказы с сайта → Сделки → Цех → Склад → Каталог сайта → Сводный отчет → Финансы → Зарплата → Чат → … → Сотрудники → Профиль → Настройки.

## 3a. Публичный сайт и интернет-магазин

Витрина живёт в том же приложении (Inertia + Vue), на публичных маршрутах
(`routes/site.php`) и **читает каталог прямо из ERP** — отдельной базы товаров
и отдельной админки нет.

- **Адреса:** `/` — главная, `/katalog`, `/katalog/{slug}` — карточка,
  `/konfigurator`, `/korzina`, `/oformlenie`, `/zavod`, `/proekty`, `/kontakty`.
  ERP осталась на своих адресах (`/login`, `/dashboard`, `/deals`…).
- **Дизайн:** две темы на одной обёртке `.site` — ночная (самый тёмный тон
  #0A0A0C, чистого чёрного нет) и дневная (молочно-белый #F8F9FA, айвори,
  тёплый камень). Переключатель в шапке, выбор запоминается, по умолчанию
  берётся системная тема. Палитра живёт в CSS-переменных, поэтому вся
  существующая вёрстка следует за ними без правок; **ERP этих токенов не
  использует и остаётся светлой всегда**. Поверхности — матовое стекло
  (`.card`): полупрозрачный фон, `blur(20px) saturate(160%)`, тонкая рамка,
  мягкая тень, скругление 20–24px. **Кнопки — мягкий прямоугольник 12px**, не
  капсула: у карточек радиус вдвое больше, и таблетка внутри читалась бы как
  элемент из другого набора. Круглые только кнопки-иконки в шапке. Иерархию
  держит заливка — главная кнопка литая латунная, второстепенная и «В корзину»
  прозрачные с контуром в 1px того же тона, что и текст. «В корзину» несёт
  микро-стрелку →, она сдвигается вперёд при наведении. **WhatsApp —
  фирменный зелёный** с иконкой: цвет работает указателем, посетитель узнаёт
  канал раньше, чем читает подпись.
- **Фон** — один непрерывный слой света на всю страницу (`.site-ambience`):
  три фиксированных пятна перетекают друг в друга по прокрутке (тёплое
  сверху, холодное в середине, глубокое внизу). Секции фон не красят: любая
  посекционная заливка обрывалась бы на границе и давала шов. Меняется
  только `opacity` — рендер-цикл Three.js на первом экране не страдает.
- **Главная — 3D-сборка двора при скролле** (технология), а реальные объекты
  показываются ниже, в блоке «Реализовано · Объекты по Казахстану»: карточка =
  фотография объекта + объём крупной цифрой поверх снимка, под ней город, год,
  название и состав работ. Пока фото не загружено, вместо него рисунок
  перевязки (`.paving-pattern`) — блок не разъезжается и выглядит цельно.
  Те же карточки на странице «Проекты».
- **Объекты сайта** (ERP → «Объекты сайта», таблица `site_projects`,
  ведут admin/director/financist): название, город, год, объём, состав,
  описание и фотография (ужимается тем же `MediaService`). Стартовый набор из
  `SiteContent::projects()` подставляется, только пока таблица пуста — если
  объекты заведены и скрыты, это решение владельца, витрина его не подменяет.
- **3D-история на главной:** Three.js собирает двор по мере скролла (одна
  плитка → раскладка → бордюры → скамья, вазоны, урна → общий план).
  Геометрия процедурная, GSAP ScrollTrigger отдаёт прогресс, Lenis сглаживает
  скролл. Освещение — IBL через `PMREMGenerator` + `RoomEnvironment` (без
  внешних HDRI-файлов) плюс ACES-тонемаппинг и мягкие тени: материалы читаются
  как бетон, а не как пластик. Сцена грузится отдельным чанком и только при подходе к секции,
  простаивает вне экрана и уважает `prefers-reduced-motion`.
- **3D-конфигуратор двора** (`/konfigurator`, **выключен по умолчанию** —
  включается в ERP → Настройки, галочка «Показывать 3D-конфигуратор»;
  пока выключен, пункта нет в меню, кнопки на главной ведут на «Контакты»,
  а сам маршрут отдаёт 404): коллекция плитки, цвет,
  раскладка (со смещением / шов в шов / ёлочка / плетёнка), размеры участка,
  бордюр по периметру и малые формы. Сцена — InstancedMesh с орбитальным
  управлением; количество, запас на подрезку и стоимость считаются по
  `specs.pieces_per_m2` и ценам каталога. Итог уходит в корзину или в WhatsApp.
- **Каталог:** категории (сегмент-контрол со скользящей плашкой — переход
  сохраняет состояние компонента, поэтому плашка едет с текущего места, а не
  из угла), поиск, фильтр по цене, сортировка, избранное и «недавно
  смотрели» (localStorage), похожие товары, характеристики, документы. Пока в карточке ERP нет фото, превью рисуется вектором по типу
  изделия и выбранному цвету (`ProductVisual.vue`).
- **Покупка:** корзина в сессии (цены всегда из ERP; название, снимок и
  палитра берутся из карточки при каждом показе, поэтому корзина, собранная
  по-казахски, читается по-русски сразу после переключения языка), позиция
  показывает снимок товара — а где фото ещё нет, ту же векторную схему, что и
  каталог. Кнопки корзины и оформления — спокойный набор `.btn-clean-*`:
  плоские, без градиента, заливка появляется только при наведении.
  «Оформить заказ» и «Очистить корзину» одной формы, разводит их цвет —
  латунь бренда против красного; алое пятно в покое читалось бы как ошибка. Калькулятор площади,
  калькулятор бордюра, прикидка доставки по городу, оформление заказа и
  заказ в WhatsApp одной кнопкой.
- **Заказы:** `orders` + `order_items`, номер `ZT-2026-0001`. Заказ сразу виден
  в ERP («Заказы с сайта»), менеджеры и руководство получают уведомление,
  кнопка «В сделку» создаёт сделку через `DealNumberService` на первом этапе
  обычной воронки — состав заказа уходит в описание.
- **Контент** (контакты, филиалы, цифры, этапы производства, преимущества,
  FAQ, проекты, тарифы доставки) — `App\Support\SiteContent`: значения по
  умолчанию перекрываются настройками ERP, отдельной CMS нет.
- **Каталог в ERP** (`/catalog`, права `product.*`): карточки, категории,
  характеристики «ключ: значение», палитра «Название #HEX», публикация,
  «на главной», «в наличии». Кэш витрины сбрасывается при каждом сохранении.
  ERP-маршруты каталога работают по `id` (slug меняется вместе с названием).
- **Медиа карточки** (вкладка «Фото, 3D и документы»): загрузка фото
  (`MediaService` ужимает до 1600 px + превью 600 px, витрина отдаёт srcset),
  выбор главного снимка, **привязка снимка к цвету изделия** (выбор цвета в
  карточке переключает галерею на фото этого цвета; снимки без привязки видны
  всегда, а если фото нужного цвета нет — витрина честно пишет об этом),
  документы (паспорт, сертификат, схема укладки) и
  необязательная 3D-модель. Кнопка **3D** помечает фото как ТЕКСТУРУ:
  этим снимком 3D-сцена главной и конфигуратор красят изделие вместо ровного
  цвета (`CatalogService::sceneAssets()`), а GLB-модель заменяет процедурную
  геометрию скамьи и вазона. Лучший исходник для текстуры — фрагмент
  поверхности сверху при ровном свете.
- **Форматы 3D:** **GLB/GLTF** — один самодостаточный файл (предпочтительно);
  **OBJ** — комплектом `.obj` + `.mtl` + текстуры одной загрузкой: `.mtl`
  ссылается на файлы по именам, поэтому комплект кладётся в общую папку
  `catalog/{id}/models` с сохранёнными именами (`MediaService::storeModelSet`).
  OBJ без `.mtl` загрузится, но изделие будет серым — интерфейс об этом
  предупреждает. **Что где работает:** фото-текстура — только для плоских
  повторяющихся поверхностей (плитка, бордюр); для урн, скамей и вазонов
  снимок нельзя натянуть на объём, там работает модель. Если у категории
  загружено несколько моделей (два типа вазона), сцена расставит РАЗНЫЕ, а не
  копии одной. Модель вписывается в габарит своего места по всем трём осям. Загрузчик витрины (`resources/js/site/gltf.js`) выбирает
  GLTFLoader или OBJLoader+MTLLoader по расширению; при ошибке возвращает null,
  и сцена рисует процедурную геометрию.
- **Первый экран на выбор** (ERP → Настройки → Сайт): `scene3d` — 3D-сборка
  двора при прокрутке (по умолчанию), `showcase` — витрина-слайдер по
  категориям. Витрина требует загруженных снимков категорий; нет снимков —
  сайт честно остаётся на 3D-сцене, пустого слайдера не будет. Управление
  слайдером: клик по карточке, стрелки, ←/→, свайп; автопрокрутка 7 с встаёт
  при наведении, фокусе, скрытой вкладке и `prefers-reduced-motion`, после
  ручного переключения молчит 15 с. Активный слайд пишется в `?item=`.
  Быстрые клики складываются в очередь — применяется последний.
- **Категории сайта** — отдельная страница ERP («Каталог сайта → Категории»):
  список со снимком на клетчатой подложке (прозрачность видно сразу),
  счётчик «без снимка», создание, правка, порядок, акцентный цвет и до
  четырёх подписей к снимку (выноски вокруг изделия на витрине). Подписи
  относятся к кадру категории; пусто — соберутся из характеристик самой
  дешёвой позиции раздела.
- **Снимок категории:** PNG или WebP с прозрачным фоном, предмет вырезан,
  1600×1600, все категории в одном масштабе и с одной точки. JPG отклоняется
  на валидации: без альфа-канала кадр становится белой заплаткой на тёмной
  теме. `MediaService` сохраняет PNG как PNG (альфа цела), фотографии
  по-прежнему сжимает в JPEG, и **рядом с каждым снимком кладёт копию в
  WebP** — он вдвое легче и держит прозрачность; витрина отдаёт его через
  `<picture>`, исходник остаётся запасным. Для снимков, загруженных раньше,
  копии дозаписывает `php artisan media:webp`.
- **Кнопка связи** — плавающая, на каждой странице витрины: WhatsApp,
  Instagram и звонок раскрываются из одной кнопки. Контакты берутся из общих
  данных Inertia (те же, что в шапке и подвале), ничего не зашито. Внешние
  ссылки открываются с `rel="noopener noreferrer"`; адрес Instagram проходит
  проверку схемы и на клиенте, и правилом валидации — Vue подставляет `href`
  как есть и не экранирует `javascript:`.
- **Слой глубины** (`PavingParallax`) — снимки брусчатки над 3D-двором,
  движение считается от прогресса, который ScrollTrigger первого экрана уже
  вычисляет: своего триггера и слушателя скролла нет. Отрисуется сам, как
  только у коллекций брусчатки появятся фото.



## 3b. Два языка: казахский и русский

Основной язык — **казахский**, второй — русский. Оба живут во всей системе:
на витрине, в контенте каталога и в интерфейсе ERP.

- **Адрес решает язык витрины.** `/katalog` — основной язык, `/ru/katalog` —
  русский. Сохранённый ранее выбор адрес НЕ перебивает: иначе присланная
  ссылка открывалась бы не на том языке, на котором её отправили, а поисковик
  получал бы разный текст по одному URL. `/kk/katalog` при казахском основном
  отдаёт 301 на канонический адрес — дублей в индексе нет. В `<head>` —
  `canonical` и `hreflang` на обе версии.
- **Основной язык настраивается** в ERP → Настройки → «Язык по умолчанию».
  Переключили на русский — префикс автоматически переезжает на казахский,
  без `route:clear` на проде: маршруты зарегистрированы на все языки сразу
  (`site.*`, `kk.site.*`, `ru.site.*`), а выбор делает `SetLocale`.
- **Язык в ERP** берётся из карточки сотрудника (`users.language`), затем из
  сессии, затем из настройки. Пусто = «как в настройках»: колонка стала
  необязательной, и смена языка компании доходит до тех, кто свой не задавал.
  Уже заведённым сотрудникам русский оставлен намеренно.
- **Переключатель** — в шапке сайта и в шапке ERP, подписи **KZ / RU**. Код
  языка при этом остаётся `kk` (стандарт ISO): на нём держатся адреса,
  словари и атрибут `lang`, а «KZ» — только надпись на кнопке.
- **Позиция прокрутки при смене языка сохраняется.** В ERP это делает Inertia
  (`preserveScroll`), на витрине переход полный — адрес другого языка браузер
  считает новой страницей и уводит в начало. Поэтому позиция запоминается в
  `sessionStorage` перед уходом и возвращается после загрузки
  (`resources/js/site/localeScroll.js`). Возврат повторяется несколько кадров:
  картинки грузятся лениво, и сразу после mount страница ещё короче нужного —
  один `scrollTo` упёрся бы в её текущий конец. Любое движение посетителя
  (колесо, касание, клавиша) прекращает попытки — спорить с ним нельзя.

### Где лежат тексты

| Что | Где | Чем правится |
|---|---|---|
| Витрина | `lang/{kk,ru}/site.php`, ключи вида `site.nav.catalog` | ERP → Переводы |
| Интерфейс ERP | `lang/kk/erp.php`, ключ = русский оригинал | ERP → Переводы |
| Общее (пагинатор) | `lang/{kk,ru}/app.php` | ERP → Переводы |
| Каталог, разделы, объекты сайта | таблицы `*_translations` | вкладки KZ/RU в карточке |
| Контакты, FAQ, площадки, тарифы | настройки, суффикс языка в строке | Настройки → Сайт |

**Интерфейс ERP переведён по принципу gettext:** ключом служит сам русский
текст (`$e('Сохранить')`). Поэтому у каждой строки уже есть осмысленный
запасной вариант — забыли перевести, сотрудник видит русскую фразу, а не
`erp.deals.save`. По той же причине запасного языка у этой группы НЕТ:
подстановка чужого языка означала бы казахский текст на русском интерфейсе.
У витрины ключи непрозрачные, и там запасной язык, наоборот, включён.

Два теста держат словарь и шаблоны в согласии: `ErpInterfaceLocaleTest`
падает, если в шаблоне появилась непереведённая строка или в словаре осталась
строка, которой больше нет в шаблонах.

### Переводы контента

Базовая колонка (`products.name`) остаётся значением по умолчанию, а таблица
переводов перекрывает её для языка. **Пустой перевод — это не перевод:**
незаполненное поле откатывается к базовому значению, иначе полупереведённая
карточка показывала бы покупателю пустое место. Подстановка вызывается явно
(`localized()`), а не прячется в `toArray()`: иначе форма ERP показала бы
переведённый текст и сохранила его обратно в базовую колонку.

Поиск по каталогу ищет и по переводам: на казахской витрине покупатель вводит
казахское название, а в базовой колонке лежит русское.

У текстов из настроек (FAQ, площадки, тарифы) перевод лежит в той же строке
под суффиксом языка — `city` и `city_kk`. Отдельные копии списков заставили бы
дублировать и цифры (тарифы, годы, площади), а они на всех языках одни и те
же и разъезжались бы при первой же правке.

### Страница «Переводы»

Показывает **весь** словарь, а не только строки из базы: слева текст из
поставки, справа правка владельца. Пустая правка означает «вернуть как в
поставке» — строка удаляется, и снова работает файл. Разделы: Сайт, Интерфейс
ERP, Общее; больше тысячи строк, поэтому есть поиск и лимит выдачи.

## 4. Логика денег (единые формулы)
- **По сделке:** налог = бюджет × ставка (Setting `tax_percent`, 3%); остаток = бюджет − налог − confirmed-расходы; маржа % = (бюджет − расходы)/бюджет (ДО налога — по ней ступень бонуса); бонус = ставка(маржа) × остаток × min(1, оплачено/бюджет); **ручной % бонуса** по сделке (`deals.bonus_rate_override`, ставит financist/admin) перекрывает ступени ВО ВСЕХ расчётах (единый `PayrollService::marginBonus`).
- **Личный % сотрудника** (`users.bonus_percent`, поле «% бонуса» в карточке):
  бонус = этот % × ЧИСТЫЙ ОСТАТОК сделки. Приоритет ставки: ручной % по сделке
  (`bonus_rate_override`) → личный % сотрудника → ступени от маржи (для тех,
  кому процент ещё не задан). Значение кэшируется на время запроса и
  сбрасывается при сохранении сотрудника.
- **Ступени бонуса (запасной вариант):** ≤10%→0; 11–15→5%; 16–20→7%; 21–30→10%; 31–40→13%; ≥41→15% (`PayrollService::bonusRateForMargin`).
- **Доход компании** = фактические платежи по won-сделкам; **расход** — все confirmed сразу; «Доход (Сводный отчёт)» = Σ(остаток − бонус) по не-отменённым сделкам. Один источник правды: PayrollService (companyTotals/perUser/dealBreakdown) + FinanceService (companyBalances/dealsIncome).

## 5. Ключевые бизнес-правила
- **Мультикомпанийность:** сейчас одна фирма — **QAZAQ TAS (код QT)**, номера сделок `QT-001`. Механизм фирм в коде сохранён: вторая фирма заводится строкой в `companies` (+ своя воронка в Настройки → Этапы), данные изолируются политиками (`worksInCompany`), режим «Все» — сводно.
- **Порядок этапов.** Воронка на странице — это этапы фирмы ПЛЮС общие
  (`company_id = null`), и порядок считается по этому же набору. Раньше
  нумерация и стрелки шли строго по `company_id`: общие этапы жили со своей
  нумерацией, в списке появлялись два этапа с `order = 1`, новый этап получал
  занятый номер, а стрелка «выше» искала соседа только среди «своих» и упиралась
  в «этап уже первый», хотя выше на экране были другие. Обмен местами с соседом
  убран целиком — порядок задаётся ОДНОЙ операцией (`stages.reorder`): клиент
  шлёт список id сверху вниз, сервер сохраняет 1..N без дыр. Ту же операцию
  вызывают и перетаскивание за ручку ⠿, и стрелки. Посторонний id из запроса
  чужие этапы не переставит. У цеха нумерация внутри каждого города своя.
- **Спец-этапы по stage_type** (contract/design/shop_gate/logistics/assembly/act/esf/payment_won) — переименование не ломает логику; тип уникален в воронке.
- **Документ на этапе:** галочка «Требуется прикреплённый документ» в
  Настройки → Этапы. Пока к сделке не приложен файл, вперёд она с этого этапа
  не идёт (назад — идёт); причина показывается красным баннером.
- **Гейт-задачи этапов:** текст/роль/срок на этапе; при входе — задача каждому активному сотруднику роли + уведомление; сделка дальше не идёт, пока не закрыта. Из коробки: «Замер и расчёт» → технолог (3 дня), «Закуп сырья» → снабженец (5 дней), «Акт утверждение» → бухгалтер (3 дня).
- **Роли по этапам:** менеджер до Акта; АКТ/ЭСФ/Оплата — только financist/admin; после Акта менеджеру read-only. Оплата успешно НЕ требует полной оплаты (остаток — в дебиторку). Удаление сделок — только admin (+bulk); каскад: заказ цеха отменяется, ссылки помечаются «сделка удалена».
- **Нумерация сделок:** `QT-001` по фирме; считаются только ЖИВЫЕ (при удалении номер освобождается: `…#del{id}`); удалили все — снова с 001.
- Счёт с суммой 0 запрещён; статусы счетов — только пересчётом платежей; расход/счёт не переставить на чужую сделку.
- Просрочка: ЭСФ/won исключены, Акт — просрочен; и сделки, и заказы цеха.

## 6. Скорость и безопасность
- **Перф:** OPcache на проде обязателен; после каждого деплоя `php artisan optimize`; индексы под горячие запросы; чат/экраны не поллят из фоновых вкладок; статика с `Cache-Control: immutable, 1y`; код-сплит по страницам. Слайды витрины кэшируются (`catalog.hero_slides`) — считались на каждой загрузке главной, 13.6 мс → 0.8 мс. Анимации витрины идут только через `transform`/`opacity`; волна на кнопке связи проходит четыре раза и затихает, а не крутится вечно.
- **Безопасность:** `SecureHeaders` — nosniff, `X-Frame-Options: DENY`, Referrer-Policy, Permissions-Policy, HSTS при HTTPS и `Content-Security-Policy-Report-Only` (пока только собирает нарушения; перед переводом в блокирующий режим неделю понаблюдать за отчётами — Vue раздаёт инлайн-стили, зерно фона лежит в `data:`-URI, шрифты приходят с fonts.bunny.net). Принудительный HTTPS в production, троттлинг логина и публичных форм, скрытые файлы в `public/` не отдаются (403). На витрине `v-html` не используется вовсе: подписи пагинатора разбираются в данные, стрелки рисуются иконками. Единственное оставшееся место — иконки бокового меню ERP (`AppLayout.vue`), где SVG берутся из объекта-константы в том же файле: данных снаружи там нет. Аудит-лог, уведомления об удалении финзаписей.
- **Пароль администратора** берётся из `ADMIN_PASSWORD`. Не задан — сидер генерирует случайный и печатает один раз. Зашитого `password` в проекте больше нет.
- **Удаление медиа проверяет владение по папке:** позиция удаляет только файлы из `catalog/{id}/`, категория — из `categories/{id}/`. Путь в JSON мог быть скопирован из другой записи, и без проверки удаление стирало чужой снимок (так уже терялись фотографии каталога).
- **Бэкапы:** `./scripts/backup.sh [папка]` — дамп базы плюс архив `storage/app/public`. Фотографии, снимки категорий и 3D-модели лежат только там и в git не хранятся, без этого архива их не вернуть. Скрипт сам чистит архивы старше 14 дней (`BACKUP_KEEP_DAYS`). Расписание и проверка восстановления — в `DEPLOY.md`.

## 7. Запуск и деплой
```
composer setup                     # установка, .env, ключ, миграции, сборка фронта
php artisan migrate:fresh --seed   # чистая база + стартовые данные
php artisan serve                  # http://localhost:8000
npm run dev                        # или npm run build
php artisan schedule:work          # просрочка, дни рождения, сроки КП
php artisan test                   # перед каждым push
php artisan db:seed --class=SiteSettingsSeeder   # дефолты контента сайта в настройки
php artisan media:webp             # WebP-копии для снимков, загруженных ранее
./scripts/backup.sh /var/backups/qazaqtas        # база + загруженные файлы
```
Первый вход — `admin@qazaqtas.kz`. Пароль задаётся в `.env` (`ADMIN_PASSWORD`) **до** первого `db:seed`; если переменная пуста, сидер сгенерирует случайный и напечатает его в консоль один раз. Прод: Plesk Git Pull → `migrate --force` → `php artisan optimize`. Подробности — `DEPLOY.md`.

## 8. Что изменено относительно исходной системы (форк BAIA ERP)
- Ребрендинг: название, логотип (`public/logo-qazaqtas.svg` / `.png`), домен `erp.qazaqtas.kz`, конфиг `config/qazaqtas.php`.

      под загрузку 3D-моделей

## 10. Права: действие ↔ право

| Модуль | Действие | Право |
|---|---|---|
| Каталог, позиции | просмотр / создание / правка / удаление | `product.viewAny` / `product.create` / `product.update` / `product.delete` |
| Каталог, категории | те же, через `ProductCategoryPolicy` | те же `product.*` |
| Снимок категории | загрузка и удаление | `product.update` (это правка категории) |
| Медиа позиции | загрузка и удаление | `product.update` |
| Доска цеха | перенос по этапам | `project.view` — намеренно: у цеховых ролей нет `project.update`, изоляцию держит `assertWorkshopAccess` |

Удаление медиа проверяет владение по папке: позиция удаляет только файлы
из `catalog/{id}/`, категория — только из `categories/{id}/`. Путь в JSON
мог быть скопирован из другой записи, и без проверки удаление стирало бы
чужой снимок.

## 12. Карта файлов языка

| Файл | Что внутри |
|---|---|
| `app/Support/Locales.php` | список языков, основной язык, имена маршрутов, адреса версий |
| `app/Http/Middleware/SetLocale.php` | язык запроса: адрес для витрины, карточка сотрудника для ERP |

| `lang/kk/erp.php` | интерфейс ERP: русский оригинал → казахский |

`app.css` только собирает их и подключает Tailwind. Порядок важен: токены
объявляются раньше, чем их читают. `postcss-import` раскрывает `@import`
до Tailwind — иначе `@apply` в слоях остаётся необработанным.

к снимкам категорий, устройство слоя света.

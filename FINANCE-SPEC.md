# Финансовый контур QAZAQ TAS ERP — полное описание

> Самодостаточный документ: описывает, как устроены деньги в системе — страницы,
> роли, расчёты, правила, команды и инварианты. Годится как ТЗ для повторной
> реализации и как промпт для модели. Состояние на 16.08.2026, 511 тестов.

---

## 1. Принципы, на которых всё держится

1. **Один источник правды.** Все денежные цифры считают два сервиса:
   `FinanceService` (остатки, скоупы, доход) и `PayrollService` (бонусы, ЗП).
   Запрос «мимо сервисов» = расхождение страниц.
2. **Деньги двигает подтверждение, а не намерение.** Заявка сотрудника кассу не
   трогает; касса меняется, когда бухгалтер выбрал, откуда платить.
3. **Считает сервер, клиент показывает.** Никаких пересчётов сумм в браузере.
4. **Правило, которое нельзя обойти, живёт в БД.** Идемпотентность — на unique-
   ключах, гонки — на `lockForUpdate`, а не на условиях в коде.
5. **Ничего не угадываем по названию.** Логика этапов и категорий держится на
   кодах (`stage_type`, `ExpenseCategory::code`), которые владелец не правит.
6. **Удаление денег — событие.** Любое удаление финзаписи уведомляет СЕО и
   директора со ссылкой на хозяина записи.

## 2. Роли и доступ

| Роль | Что может с деньгами |
|---|---|
| **admin** (СЕО) | всё; единственный, кто корректирует кассу |
| **director** | видит всё, не подтверждает и не заводит |
| **financist** (бухгалтер) | подтверждает расходы, заводит расходы/поступления/долги, ведёт ЗП |
| **manager** | заявка на расход, расходы своей сделки; чужих денег не видит |
| **employee / lawyer / cook / designer / supplier** | только «Мои расходы» и своя «Зарплата» |

Право `expense.create` есть у всех ролей. `expense.delete` — только у admin и
financist (снято у менеджера и продублировано в `ExpensePolicy`, чтобы правило
пережило правку прав через админку).

## 3. Страницы

Все денежные страницы живут в общем каркасе `FinanceLayout`: одна шапка
(название + пояснение), один ряд вкладок, один контейнер, кнопки и фильтры в
общем слоте. Плитки-итоги — общий компонент `FinanceTile`.

| Маршрут | Страница | Кому | Содержание |
|---|---|---|---|
| `/finance` | Обзор | admin, director, financist | ДДС, плитки (договоры, дебиторка, касса, банк), сводка «Доход − Расходы = Чистая прибыль» с фильтром месяца, переходы в разделы |
| `/finance/invoices` | Счета | те же | выставлено / оплачено / остаток; сегодняшние + прошлые с поиском |
| `/finance/receipts` | Поступления | те же | форма поступления (нал/банк, откуда), сегодня + прошлые с поиском и периодом |
| `/finance/debts` | Задолженности | те же | дебиторка: авто по счетам + записи вручную |
| `/expenses-board` | Расходы | те же | очередь на проверку (чеки открыты) + оплаченные за месяц с фильтрами, правкой и удалением |
| `/cash-book` | Касса | те же | книга за день: начало → операции → конец, печатный «Отчёт кассира» |
| `/my-expenses` | Мои расходы | любой с `expense.create` | свои заявки, свои выплаты (аванс/долг), подача заявки |
| `/payroll` | Зарплата | `payroll.view` | ведомость: оклад/часы, бонусы, удержания, долги, поиск и отборы |

## 4. Схема данных (ключевое)

```
expenses            morph(expenseable: deal|project|null), company_id, category_id,
                    material_id, qty, amount, sale_amount, date, responsible_user_id,
                    description, file_path, type, status(draft|pending|confirmed),
                    payment_method(cash|bank|null), confirmed_by, confirmed_at,
                    employee_id, employee_payout(advance|debt), reminded_at, softDeletes
expense_categories  code (unique, служебные: employee, materials_purchase), name, is_active
employee_debts      user_id, company_id, amount, monthly_payment, payment_method,
                    expense_id, note, closed_at
employee_debt_payments  employee_debt_id, month(YYYY-MM), amount, unique(debt, month)
materials           name, unit, quantity, price (закуп), markup_pct
material_receipts   material_id, expense_id (оплата закупа), quantity, price, date

```

Индексы: `expenses.employee_id`, `expenses(employee_payout)`,
`expenses.material_id`, `employee_debts.user_id`, unique(долг, месяц).

## 5. Расходы: жизненный цикл

**Три вида записи в `expenses`:**

1. **Заявка компании** (morph пуст). Подаёт любой сотрудник с `expense.create`.
   Сервер принудительно ставит `status=pending`, `payment_method=null` — что бы
   ни пришло из формы. Категория обязательна, чек можно приложить сразу.
2. **Расход по сделке.** Заводит менеджер (только по своей сделке) или
   бухгалтер. Менеджерский ждёт подтверждения.
3. **Списание материала** (`material_id`). Авто-подтверждён, `payment_method =
   null` — кассы не касается (деньги ушли при закупе), но в маржу сделки входит.
   Сумма = количество × закупочная цена; вручную не правится.

**Подтверждение** (`ExpenseController::confirm`, admin/financist) — единственный
путь к деньгам: обязателен чек (уже приложенный или загружаемый) и способ
оплаты нал/банк. Второго endpoint нет ни у борда, ни у карточки сделки.

**Заморозка.** Признак — `confirmed_by`, а не `status`: подтверждённый
бухгалтером расход правит только бухгалтер (иначе запрет на удаление обходился
бы правкой суммы на 1 ₸). Списание материала — system-confirmed без
`confirmed_by` — для правки не заморожено.

**Удаление** — только admin/financist, любые расходы, включая pending. Удаление
списания возвращает остаток на склад. Расход-выдачу долга отдельно удалить
нельзя — отменяется вместе с долгом.

**Чеки.** Хранятся в `storage/app/private`, отдаются guard-маршрутом (автор /
`employee_id` / admin, director, financist). Фото ужимается до 1600 px при
загрузке (`MediaService::storeReceipt`), PDF и HEIC сохраняются как есть.

## 6. Касса и банк

`FinanceService::companyBalances`:

```
касса = платежи(нал) + поступления(нал) − подтверждённые расходы(нал) + cash_correction
банк  = платежи(не нал) + поступления(банк) − подтверждённые расходы(банк)
```

- **Касса — ЕДИНАЯ на холдинг** (деньги физически в одной кассе): считается без
  фильтра фирмы. **Банк — по своей фирме.**
- `cash_correction` — разница, введённая админом при инвентаризации (плитка ✎).
  История не трогается, отчёты не искажаются.
- Расходы с `payment_method = null` (заявки, списания склада) в остатки не
  входят вообще.

Скоупы вынесены в сервис (`scopeCompanyExpenses`, `scopeCompanyInvoices`) и
переиспользуются всеми страницами — копия скоупа в контроллере рано или поздно
разъезжается.

## 7. Кассовая книга (`/cash-book`)

- Параметры: день (`date`) и режим `cash | bank | all`.
- Остаток на начало — `FinanceService::balanceBefore` (тот же расчёт, что
  текущий остаток, но по операциям строго до даты): три агрегата, не выгрузка
  истории.
- Операции дня: оплаты по счетам, поступления, подтверждённые расходы — каждый
  поток по своему правилу (касса по холдингу, банк по фирме). В режиме «Общее»
  потоки складываются, но считаются раздельно.
- Порядок ленты определён явно: время → приход раньше расхода → id.
- Промежуточный остаток по строкам считает сервер.
- Печатная форма: `@media print` убирает меню и кнопки, добавляет шапку «Отчёт
  кассира» и подписи кассира и бухгалтера.
- **Инвариант:** конец дня N = начало дня N+1 = плитке Финансов.

## 8. Склад и деньги

**Закуп = момент ухода денег.** В форме прихода — «Оплата закупа»: нал / банк /
не списывать. Нал или банк создаёт подтверждённый расход категории
`materials_purchase` на количество × цену, датой прихода. Правка прихода двигает
сумму расхода, удаление прихода удаляет расход.

**Списание в сделку — движение запаса**, а не денег (`payment_method = null`).
В маржу сделки входит; удаление возвращает остаток.

**Наценка и цена продажи.** У позиции склада есть `markup_pct` (пусто — общая из
настроек `material_markup_percent`), цена продажи = закуп × (1 + наценка). При
списании цена продажи фиксируется в `expenses.sale_amount` — наценку потом
поменяют, а бонус по проданному меняться не должен.

**Двойной счёт закрыт:** в итог «Расходы» (Финансы и Аналитика) списания склада
не входят — эти деньги уже посчитаны закупом; в разбивке они видны отдельной
строкой «учтено в закупе».

## 9. Зарплата и бонусы

**К выплате** = почасовая база (часы × ставка, ставка = оклад ÷ норма месяца;
часы не введены — полный оклад) + бонус − удержания + премии − план удержания
долга.

**Бонус отдела продаж — ставка по ТИПУ сделки** (правило владельца от
21.08.2026): своё производство — `bonus_sale_percent` (1%), перепродажа
(купили → склад → продали) — `bonus_resale_percent` (2%). Обе правятся в
Настройках. Считается от остатка: сумма − налог − расходы − доля партнёра, и
пропорционально оплаченной доле сделки. Приоритет ставки: ручной % по сделке
(`bonus_rate_override`) → личный % сотрудника (`users.bonus_percent`) → ставка
типа. Маржа сделки осталась показателем здоровья (`marginPct`), на бонус она не
влияет: ступенчатая шкала и отдельный бонус за наценку склада отменены — за
перепродажу платит ставка типа, иначе за один товар платили бы дважды.

**Бонус производства — деньги за объём** (`ProductionBonusService`). Бригадир
получает за ВЕСЬ объём смены своей бригады (`foreman_rate_m2` 450 ₸/м²,
`foreman_rate_pcs` 35 ₸/шт), рабочий — за свой (`worker_rate_*`, по умолчанию 0:
ставку задаёт владелец). Ставки копируются в строку наряда — поднятая цена не
пересчитывает прошлые смены. Начисляет только наряд со статусом `confirmed`:
подтверждает мастер (admin/director), не сам бригадир.

**Бонус у человека один.** Сделки и выработка складываются:
`BonusPayoutService::accrualsByMonths` (страница «Бонусы») и
`PayrollService::perUser` (`bonus` — сделки, `bonus_production` — цех,
`bonus_total` — сумма, `payout` — оклад + обе части).

Единая точка расчёта — `PayrollService::dealBonus`; её зовут карточка сделки,
ведомость ЗП, бонус за месяц, Сводный отчёт, Аналитика и доход фирмы.

**Бонус за месяц** — `bonusByMonths` (его зовут `bonusByUserForMonth` /
`bonusByUsersForMonth`): бонус won-сделки раскладывается по месяцам ОПЛАТЫ
клиентом — сделка, оплаченная частями, отдаёт бонус теми же частями. Дата
договора на месяц бонуса не влияет (это отдельный вопрос — по ней отбирают
сделки фильтры «Месяц» на Финансах и в Сводном отчёте). Выработку цеха по
месяцам считает `ProductionBonusService::accrualsByMonths` (месяц наряда), а
складывает обе части `BonusPayoutService`. В «К выплате» ведомости идёт
НЕвыплаченный остаток бонуса, а не бонус месяца.

**Аванс** — разовая выдача: корректировка ЗП + подтверждённый расход категории
`employee` (`employee_payout='advance'`), удерживается целиком в текущем месяце.

## 10. Долги сотрудников

- **Выдача** (ЗП → раскрытие сотрудника → «+ выдать долг»): сумма, фиксированный
  платёж в месяц, нал/банк, заметка. В транзакции создаются долг и
  подтверждённый расход (`employee_payout='debt'`) — касса уменьшается сразу.
- **Гашение** — команда `debts:charge {--month=}` (расписание: 1-го числа 09:00
  за прошлый месяц). Удержание = `min(платёж в месяц, бонус месяца, остаток)` и
  **только из бонуса** (сделки + выработка цеха вместе): нет бонуса — нет записи, остаток переезжает; оклад долг
  не трогает никогда. Идемпотентность держит unique(долг, месяц) в БД.
  `balance == 0` → `closed_at`.
- **В ведомости**: «Остаток X · удержим −Y · останется Z»; «К выплате»
  уменьшается на план месяца отдельным полем `debt_charge` — аванс и долг
  независимы и не гасят друг друга.
- Отменить выдачу можно, пока по долгу нет удержаний; расход уходит вместе с
  долгом.

## 11. Целостность денег

1. **Платёж ≤ остатка счёта.** Счёт блокируется в транзакции, остаток
   перечитывается под блокировкой: двойной клик не оплачивает счёт дважды.
2. **Анти-дубль форм.** Поступление или расход с теми же автором, суммой, датой
   и описанием младше минуты отклоняется как повторная отправка.
3. **Гонка «В работу ✓».** Заявка блокируется — два клика создают одну сделку.
4. **Дебиторка** не считает отменённые счета.
5. **Итог «Расходы»** не включает категорию `employee` (там уже стоит строка
   «Зарплата»); в разбивке она видна с пометкой, кассу уменьшает честно.
6. **`finance:selfcheck`** — сверка инвариантов на живых данных: касса и банк
   против пересчёта с нуля, дебиторка против суммы остатков по счетам, ЗП против
   оклада+бонуса, счета с переплатой, стыковка кассовой книги с плитками.
   Ненулевой код возврата при расхождении.

## 12. Уведомления

- **Резолвер** (`NotificationResolver`): подтвердили или удалили расход —
  «ждёт проверки» гаснет у всех бухгалтеров; закрыли задачу — гаснут её
  уведомления у исполнителей. Поиск по `expense_id` / `task_id` в data.
- **Колокольчик**: список открыли — через 1,5 с непрочитанное помечается
  прочитанным. «Открыть» на уведомлении работает независимо.
- **Удаление финзаписи** ведёт к хозяину: расход/счёт/платёж по сделке — на
  карточку сделки, по заказу — на заказ, поступление и долг — на Финансы.
- **`expenses:notify-stale`** (09:30 ежедневно): заявки, ждущие дольше трёх
  дней, — напоминание бухгалтерии, однократно на заявку (`reminded_at`).
- Язык уведомлений фиксируется при создании (по-русски) — известное ограничение.

## 14. Обязательные инварианты (что обязано сходиться)

1. Касса и банк из `FinanceService` = пересчёт с нуля по платежам, поступлениям
   и подтверждённым расходам (+ корректировка кассы).
2. Конец дня в кассовой книге = начало следующего дня = плитке Финансов.
3. «Общее» в книге = Наличные + Банк, каждый поток по своему скоупу.
4. Дебиторка = Σ остатков по каждому неотменённому счёту (расходится только при
   переплате).
5. Итог «Расходы» не содержит ни ЗП дважды, ни списаний склада поверх закупа.
6. Бонус в ведомости = `dealBonus` по каждой сделке; плитка месяца =
   `bonusByUserForMonth`; удержание долга = то же число, что показывает план.
7. Заявка со статусом pending не влияет ни на кассу, ни на книгу, ни на итоги.

## 15. Правила разработки этого контура

- **Двуязычие:** каждая видимая строка — `$e('Русский текст')` в шаблоне /
  `tr('…')` в script, перевод в `lang/kk/erp.php`. Сторожевые тесты
  `ErpInterfaceLocaleTest` проверяют словарь в обе стороны — их не отключают,
  а чинят словарь.
- **Дизайн:** денежные страницы — только через `FinanceLayout` и `FinanceTile`;
  модалки — существующий `Components/Modal.vue`, подтверждения — `confirmDialog`.
- **Анимации:** только `transform` и `opacity`, раскладку не анимируем.
- **Скорость:** индексы сразу в миграции, `with()` на каждой выборке, выборки
  кассовой книги ограничены одним днём.
- **Безопасность:** критичные запреты дублируются ролями внутри Policy; чеки
  приватные; `status`, `payment_method`, `confirmed_by`, `employee_id` из формы
  не принимаются там, где их ставит сервер; IDOR закрыт тестами.
